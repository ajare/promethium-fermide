# A zero floor depth is a value, not an absence

Status: accepted

A Sector's floor depth override was stored with zero folded into the absence: `setSectorFloorDepth(_, 0)` recorded nothing, on the reasoning that zero lifts nothing and that is what no field already says (#1101). That was harmless while a Sector either carried a depth or carried none. It stopped being harmless the moment a Sector could *follow a type default* (#1103): "hold this Room at the unlifted position while every Room of its type lifts" is a state an author wants, and the collapse made it unrepresentable - which surfaced as the editor's Break away being disabled over a type at zero, blocking the main override use case (#1112). We took the full fix rather than the cheap one: **the presence of the field is the override, and the value that presence carries is the depth**, so zero is a value like any other and only `clearSectorFloorDepth` removes the field and puts the Sector back to following. The World schema went to 74 for it, and a document claiming an older version while carrying a zero depth is refused rather than interpreted.

## Considered options

- **The cheap workaround** - leave the storage alone, enable the button whatever the type carries, seed the input at the followed value and commit only a non-zero edit. Rejected: it unblocks the user story and leaves the hole in it. "Hold this Room still while its type lifts" stays inexpressible forever, and the editor is left explaining a control that cannot reach a value its own input can type. Cheap now, and paid for the first time an author wants the missing state.
- **A separate `overridden` flag beside the depth** - Rejected: two fields that must agree is two ways to be inconsistent, and the `optional` already *is* the flag. The distinction the feature needs is presence, so it is stored as presence rather than as a second copy of it.
- **Reading a pre-74 zero as "follow" instead of refusing it** - Rejected: the pre-74 writer never emitted a zero depth, so a document claiming schema 73 while carrying one did not come from that writer and its bytes mean nothing we can know. Guessing at a foreign document is worse than refusing it, and the refusal says which field and which version.

## Consequences

- **ADR 0023's promise is finally kept.** That ADR rejected a dense field because it "collapses 'no opinion' and 'zero' into one state, so a Sector that was never touched becomes indistinguishable from one deliberately set to zero". Under the #1101 collapse the two were still indistinguishable, just from the other side: the deliberate zero had nowhere to be written. Sparse storage only means what it claims once presence and value are independent of each other.
- **The per-type map keeps its collapse, and is not inconsistent with this.** Setting a Sector *type* back to zero still erases its entry. There the absence and the zero answer the same question identically - every Sector following the type reads 0 either way - so a stored zero would carry no fact the absence does not already carry. The Sector's zero was different because there the absence means *follow*, and pinning against a following default is a different answer.
- **Every reader that treated zero as absence had to be found.** The write, the sparse writer, the replay onto rebuilt Sectors, the editor's disabled button and its tooltips, and the seam documentation all encoded the old rule. The version guard is what stops any of them being quietly wrong about an old document.
- **Reset is a deletion, not a number the input can reach.** The author types a depth, including zero, and presses Reset to stop carrying one. The two acts cannot be confused because neither can do the other's job.
- **Schema 74 is a one-way door for zero.** A World with a pinned zero cannot be opened by a pre-74 reader at all, not merely read wrong. That is the cost of the version guard, taken deliberately: the alternative was a save that silently released every pin in the World on the next write.
