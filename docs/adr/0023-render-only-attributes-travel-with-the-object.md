# Render-only attributes travel with the object they describe

Status: accepted

Floor depth - a signed count of pixels at 1x zoom saying how deep a Sector's floor runs into the screen, which lifts the Layers behind that Sector so a flat drawing reads as depth (#1099) - had to be stored somewhere. The instinct for a render-only attribute is to keep it out of the core domain object and hold it in a side table owned by whoever draws it. We decided the opposite: **a render-only attribute lives with the object it travels with** - on `core::Sector`, on that Sector's `ConstructionRecord`, and serialized with the World - the same shape the Layer Image set binding and Sector surface variants already established. The per-type defaults sit on the `World` itself, which is the thing that owns a type scheme; nothing in this feature is held in a table keyed by Sector index. The reason is identity, not tidiness: **Sector indices are not stable across deletion.** Removing a Sector erases it from the Sector vector and remaps every index above it across cell definitions, Interaction points and their command bindings, device operations, traversal resources (landing sectors, queue lanes, door-route observation keys, extensible control sectors), paused path intents, movement goals and remembered device conditions. A side table keyed by that index has to join that remap on every structural edit, and it will be forgotten exactly once - silently handing one Room's floor depth to whichever Sector now sits at that index, with nothing failing and no diagnostic to follow. A value carried on the Sector cannot be mis-remapped: it moves, resizes and deletes with the thing it describes. The same reasoning makes the storage sparse at both levels - a Sector with no recorded depth holds nothing rather than a zero, and a type default is present only where the author set one - so "following the type" stays distinguishable from "coincidentally equal to the type", which a dense field destroys on the first write. Reset deletes the entry rather than writing a number.

## Considered options

- **An index-keyed side table, in the renderer or as a World-level map.** Rejected: it duplicates an identity the World does not have. Every edit that shifts Sector indices - Location and Facade deletion, Dumbwaiter removal, any construction-record replay that renumbers - must remember to shift this table too, and the failure mode of forgetting is not a crash but a Room quietly drawing at another Room's depth.
- **A dense field on the Sector.** Rejected: it collapses "no opinion" and "zero" into one state, so a Sector that was never touched becomes indistinguishable from one deliberately set to zero, and the follow/override distinction the author edits against cannot be recovered. Sparse storage also keeps a World with no depths saving exactly the way it saved before the field existed.
- **Overlap-based per-Sector derivation** (each Sector's offset derived from what sits directly in front of it). Rejected: it produces seams where two adjacent back Sectors disagree about how high they sit, because each derives its own height from a different neighbour, and it makes a back Sector slide when an unrelated Sector in front of it - possibly across the map - is edited. The chosen rule takes the maximum over **every Sector in the Layer in front**, giving exactly one offset per Layer and a uniform shift across the whole screen: adjacent back Sectors cannot disagree because they share one number, and a Sector's depth changes nothing on its own Layer or on any Layer in front of it. A Layer with no Sectors contributes a maximum of zero, so the recursion needs no fallback rule.
- **Clamping a back Sector so it always covers the apertures in front of it.** Rejected: it re-couples a back Sector's position to which holes the front Layer happens to have, so the same Room would sit at different heights in different Worlds for reasons no author can predict. The aperture is a hole in the front wall, measured off the front Sector's own geometry while that Sector's lift is in force, and it does not move; where the shifted back Layer no longer covers it, the void shows through. No diagnostic fill either - the gap is information the author tunes against, not something to hide.
- **Caching the per-Layer offsets on the World behind an invalidation flag.** Rejected: the flag would have to be cleared by the authoring seam, by undo, by redo, by World load and by World rebuild, and one missed path leaves the picture disagreeing with the panel the author is reading the number off. The array is at most `CORE_MAX_LAYERS` entries and the walk is over Sectors the renderer is about to visit anyway, so it is recomputed once per frame and cannot be stale for longer than a frame.
- **Threading the offset through every draw signature.** Rejected: a change to the whole renderer for one value. The lift is carried as an ambient in the world-to-screen mapping, installed by a scope at the top of the Sector pass and restored on every exit. The hazard is honest and accepted: a pass that forgets to install or restore it draws content at the wrong height.

## Consequences

- **The rule generalizes.** The next render-only attribute that belongs to a Sector goes on the Sector and its construction record, not into a table keyed by Sector index. The argument is about the key, not about render-only-ness: a table keyed by a stable identity (Agent id, Marker id, Access permission id) does not carry this hazard; a table keyed by a position in a vector does.
- **A Sector's own depth never moves itself; it moves everything behind it.** The value an author reads for one Sector is its Layer's accumulated offset plus that Sector's own effective depth - its override where it has one, its type's default where it does not - and the panel shows the two halves beside the sum so the number stays auditable.
- **Everything the Sector pass draws travels together under the lift** - tiles, thresholds, transit geometry, objects and Furniture, the Agents standing on its floor, its own floor-and-ceiling clip and the selection highlight. Partial application was rejected because it sinks Agents through their own floor, slides transit cars out of their shafts, and leaves the Sector clip cutting the top off the tiles it is meant to be framing.
- **Passes that draw world-space content rather than Sector content** - the grid, the player transport selector - run with the lift at zero, and the editor's screen-to-world inverse subtracts the visible Layer's lift so picking, dragging, resizing, variant painting and Agent drops stay aimed without each caller correcting itself.
- **The Location Plan is a separate renderer and is deliberately untouched**: a plan view reports positions, not a perspective picture.
- **The axis is the Layer axis, not the Level axis.** Floor depth says how far a Layer is pushed on screen; it is not a vertical floor position and does not vary per Level. CONTEXT.md keeps it clear of Local depth and Layer, which sit one word away and mean something else entirely.
- **The authoring band is one Level either way** (`CORE_LEVEL_HEIGHT_PIXELS`, 320 px), refused at the write rather than clamped at draw time, so a mistyped 5000 cannot fling every Layer behind the Sector that carried it off the screen and leave the author hunting for the one Sector responsible.
- **The void left by a shifted back Layer is a deliberate outcome.** The fix for an unwanted void is a smaller depth value, not a renderer rule.
