# Station configuration documents

The Station Flow tab's New, Open, Save and Save As controls operate on a separate Configuration draft, not the World. Open replaces that draft after confirmation if it has unsaved changes; Apply settings in the Station Systems tab is still the only way to change the World. Saving does not pause or reset a simulation. Recent configuration paths are stored separately from recent Worlds.

A configuration document is YAML with `schemaVersion: 98` (schemas 96 and 97 remain readable; omitted fields use their defaults), the same `stationSystems` map written by the World serializer, and an optional `layout` map. Layout records view pan and zoom and node coordinates keyed by type, id and occurrence; it is never a simulation input. Missing layout is generated by the Flow view. The `stationSystems` map is shared with World persistence, so configurations can be opened against other Worlds without changing their current settings. Invalid files leave the current draft and its undo history intact. In a configuration draft, any entry whose reference does not resolve - a Transfer's stores, a Conversion's endpoints, a radiator's reservoir, a chiller's loop, a generator's fuel, a crew's compartment, and so on - stays in the draft and appears as a broken (red) link on the canvas; the file still opens. Every other rule keeps its full strictness: an invalid value anywhere, including on a broken entry's own fields checked before the reference, refuses the file. Apply settings re-validates the whole configuration strictly, so broken wiring never reaches the World.

In the Flow canvas, select a Store or Transfer and press Delete (or use **Delete selected node**) to remove it from the draft. When its authored connector links have referrers, the confirmation counts them before any change; cancelling keeps the draft and history unchanged. Confirmation clears every mapped reference and removes the node as one undoable change. Unlinked nodes need no confirmation. Deletion is unavailable in drafts containing entry families whose references have no core-owned mapping yet, even for an otherwise isolated Store or Transfer; other projected node types likewise cannot be deleted from Flow yet. Derived service nodes are never authored.

A placed Conversion arrives with one input and one output connector and can be grown with the `+` affordance below its port columns to four connectors per side; `−` removes the newest one, and neither affordance is offered past the limit, so the required floor of one input and one output can never be stripped. Every grown connector is a real connector: it takes drag-to-connect links and is judged by the same core constraint rules as fixed ones, writing its own flow of the conversion entry. Grown slots left unwired read as unused rather than missing. The Solar array is placeable and shows its implicit edge to the shared electrical pool; the pool itself renders as a derived service node - dashed, inert, with no draggable connectors and absent from the type combobox - and any link dropped on it, or click aimed at it, is refused with a reason naming it as derived. Placement, growth, shrinkage and wiring each commit one shared-history entry.

Saves use the same exclusive temporary-file and atomic-replacement writer as World documents; an unsuccessful write does not mark the draft saved.

## Material identity (#699)

Every Resource store offers **material identity** in both the form and Flow
inspector. Empty is visibly **Unclassified**, including in legacy documents.
An explicit ID is a stable, case-sensitive substance key: 1–64 ASCII characters,
starting with `a`–`z`, followed by lowercase letters or digits, with single
hyphens separating segments. For example: `water`, `oxygen`, `carbon-dioxide`,
`atmospheric-nitrogen`, `nutrient-nitrogen`, or `custom-feedstock-2`.
Spaces, uppercase letters, leading/trailing or repeated hyphens are refused,
not silently normalised. Custom materials need no separate registry.

The same ID identifies the same material across stores. It is independent of
the store ID, unit, hazard class and compound composition. A compound's material
ID names the compound, not its constituent decomposition. No identity is guessed
from any of those fields: even a legacy store named `oxygen` in `kg` remains
unclassified. This slice does not resolve identities from equipment relationships
or change intrinsically identified atmospheric gases or Biological populations.

Assignment changes only the Configuration draft until **Apply settings**.
Draft undo/redo, applied World history, Reset and structural restoration retain
identity. Both standalone and World documents save optional
`stationSystems.stores[].materialId` under schema 98; omission remains empty.
Invalid identity refuses configuration application or loading atomically. Reading
older documents does not dirty or rewrite them. Identity is observation metadata:
it does not change allocation, transfer compatibility, hazard segregation or
chemistry, nor claim a complete material accounting boundary.

## Connection design properties

Click a connection curve to show **Connection properties** in the reserved
inspector column. This includes automatic electrical connections; their design
properties are editable even though their membership in the shared pool remains
automatic. Selecting a connection does not select or author a Derived service node.

Each connection has an independent physical connection type override and a
maximum throughput rating, where a flow rate is meaningful. Defaults are
**Automatic** and **1e12** in the displayed rate unit: kW for power/thermal flows,
the Resource store's native unit per second for material flows involving a Store,
or kg/s for other material flows. Ratings must be positive and finite. On physical
material, electrical, and thermal connections, the applied simulation caps
**connection input first**, then applies efficiency. Carrier overrides only change
presentation; they do not change enforcement, compatibility rules, link
cardinality, or automatic electrical pool membership. Non-physical relationships
do not offer a throughput field or a carrier override.

Every connection, including automatic power and non-physical relationships, also
has **Efficiency**, default **1.0**, in the inclusive range **[0, 1]**. For physical
connections it is the delivered fraction of accepted input: an input cap of
10 kg/s and efficiency 0.9 delivers at most 9 kg/s. Receiver demand is compensated
upstream within available supply and the input cap. At zero efficiency, actively
requested input is entirely lost; no demand means no flow. Non-finite and
out-of-range values are refused. Older connection entries without `efficiency`
load with 1.0.

Undelivered input is an explicit external connection loss, not returned to the
source or injected as waste into another reservoir. Produced heat blocked by an
input cap is retained at its source, separately from transmitted/lost heat, and
can enter the connection in later ticks. Non-physical relationships retain
informational ratings only; these include controls, cooling-service allocations,
ambient biological exchanges, circulation gates, schedules, delivery/waste-ejection
and airlock events, maintenance, and outages. Editing or saving properties still
changes only the Configuration draft until **Apply settings**. Applying non-default
physical throughput or efficiency makes the simplified scenario forecast explicitly
unavailable: it does not yet project transport constraints. Styling-only and
non-physical properties do not disable forecasts. See
[forecast scope](station-systems.md#scenario-forecast-420).

Carrier overrides and ratings are sparse entries in `stationSystems.connections`,
not layout. For example, the input connection of a Transfer named `move` fed by
Store `a` can carry:

```yaml
connections:
  - ownerType: Transfer
    ownerId: move
    reference: Source
    relation: Source
    peerType: Store
    peerId: a
    physicalType: Liquid pipe
    maximumThroughput: 1000000000000
    efficiency: 1.0
```

Omitting an entry uses that connection's defaults without materialising a saved
entry. **Reset connection properties** restores those defaults. Properties travel
through standalone configuration and World save/load, and through configuration
undo/redo. **Rename selected node** preserves them at either endpoint;
disconnecting a reference, shrinking away its port, deleting an endpoint, or
rewiring it removes the old instance's properties. Reconnecting starts with
defaults; undoing a disconnect restores its properties along with the connection.
Schema 97 protects these authored fields from silent loss in older readers.
